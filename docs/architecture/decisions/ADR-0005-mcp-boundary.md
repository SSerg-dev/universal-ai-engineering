# ADR-0005 — One Explicit MCP Boundary

- Status — Selected for Phase 3 implementation; architectural review pending
- Date — 2026-11-09
- Extends — ADR-0004

## Scope

Iteration 3 exposes one local read-only MCP capability, read_doc, through the existing registry under the host-owned alias mcp_read_doc. A controlled child process serves the existing Markdown snapshot. Explicit iteration 3 selection and an operator consent grant are required. Iterations 1 and 2 retain their entry points and behavior.

The chosen transport is stdio. The operator supplies the executable, compiled fixture-server path, and trusted fixture root. Document IDs and model arguments never influence a command, executable, environment, or filesystem path. The child receives the SDK's restricted default environment, and its stderr is discarded. No external service, account, credentials, HTTP MCP endpoint, provider, sampling, elicitation, or remote instruction execution is introduced.

## Protocol and dependency selection

Pin MCP revision 2026-07-28 and the official @modelcontextprotocol/client and @modelcontextprotocol/server packages at 2.4.0. The official registry returned matching names/versions, the modelcontextprotocol/typescript-sdk repository, Node >=20 compatibility, and integrity metadata. Existing Zod 4.6.5 satisfies the SDK's ^4.2.0 dependency.

The client uses versionNegotiation with a 2026-07-28 pin and no legacy fallback. Discovery is checked before listing tools or invoking the capability. The server refuses legacy connections. Modern-era metadata is per request. The SDK handles protocol mechanics while the host validates its selected capability and result independently.

Dependency admission is recorded separately from the original Phase 1 human-accepted pins in [the Phase 3 admission record](../../reviews/DEPENDENCIES-03.json). Selection is made under the user's instruction to continue implementation through the roadmap. It does not claim an additional human exact-package approval. The record stays planned until installation, then exact root/version checks include the two additions while preserving all original pins and categories.

## Trust boundaries

1. Consent is a host-owned grant for the exact server ID uaos-docs and remote tool read_doc. A denied grant prevents session construction and child spawning. Server annotations never grant permission.
2. Discovery must report the pinned modern era, protocol revision, expected server identity, and tools capability. Unsupported negotiation is a safe boundary failure.
3. The selected tool must appear once in a bounded tool list and advertise the exact locally expected input/output JSON schemas. Other tools are never registered or invoked. Metadata descriptions and annotations are data and never become model instructions or policy.
4. Arguments pass the local ReadDocInputSchema before any remote call. Results must contain valid structured ReadDocOutput, a consistent text rendering, a complete non-error result, and matching correlation receipts. Oversized, malformed, error, unsupported, or contradictory results fail before the second model request.
5. Every invocation has opaque runId and callId values generated by the loop. The registry forwards them through a defaulted optional context. The MCP adapter sends them in namespaced request metadata and requires the same values in response metadata. Existing tool events and the correlation receipt link the protocol call to its run without persisting raw arguments or results.
6. The caller signal and request deadlines propagate through connect, list, call, and teardown. A session is closed in finally after success, rejection, cancellation, or transport failure. The SDK owns child cleanup. Registry cancellation still bounds a noncooperative async return.

The protocol client has a bounded discovery probe, zero retries, one tool-list page, and a 128 KiB stdio read buffer. The adapter admits a maximum 64 KiB serialized tool result. The host default gives the MCP invocation 4000 ms within the existing 5000 ms run deadline. Each read uses a fresh session to keep invocation ownership and cleanup explicit.

## Contracts

Core contracts include a ToolCallContext with filename-safe opaque run/call IDs, a fixed MCP consent grant, a normalized discovery result, and a narrow McpSessionPort. SDK types remain entirely in adapters. The existing tool registry and shared loop keep their algorithms. The optional call context preserves existing two-argument handlers and stand-alone registry calls. Registered-run composition opts into includeCallContext only for MCP, preserving Phase 2 handler arity and its previously supported in-memory ID formats.

The adapter normalizes consent, context, negotiation, metadata, argument, result, and transport failures to host-owned MCP boundary codes. Registry/public failures retain the previous vocabulary. Cancelled runs retain CANCELLED, overall deadlines retain TIMEOUT, and metadata/result rejections become TOOL_FAILURE with safe tool diagnostics. No raw server exception is public or durable.

## Acceptance

The [Phase 3 plan](../../../.planning/phases/UAOS-03-mcp-boundary/03-01-PLAN.md) defines contracts before SDK installation and adapter code. Tests must prove denied consent performs zero session work, altered metadata prevents calls, annotations cannot grant access, result/correlation mismatches fail closed, cancellation closes the session, child shutdown completes, and a real pinned stdio exchange runs through CLI and HTTP while earlier iterations remain green.
