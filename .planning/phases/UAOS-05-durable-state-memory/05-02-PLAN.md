# 05-02 — Durable Resume and Explicit Memory

## Tasks

1. Implement the conversation service with validated unknown store responses, idempotent replay, stable executor context, bounded cancellation settlement, and explicit memory/recovery operations. Prove behavior using a deterministic fake store and executor.
2. Implement PostgreSQL transactions, row/version/lease checks, atomic safe audit, expiry filters, and physical purge. Prove restart persistence, concurrency, fencing, rollback, retained results, memory isolation, and metadata privacy in the disposable database.
3. Expose explicit iteration 5 conversation/memory CLI and HTTP operations. Preserve earlier entry points and grounded execution; add context as data and correlate the planned run ID with JSONL.
4. Write teaching/evidence and requirement/threat coverage. Run all offline and live database checks before marking implementation complete. Review, approval, and stability remain separate.

## Acceptance

- Cached identical requests execute zero model/tool work; reused keys with different input fail.
- Reservation, memory mutation, and settlement obey version, busy, lease, and expiry rules.
- An expired running turn needs explicit recovery; a late executor cannot overwrite it or resume its old key.
- A cancelled agent result can settle with an independent bounded signal. Failed settlement never claims a durable completed turn.
- Memory writes/deletes are explicit, conversation-scoped, TTL-bounded, audited, and absent from raw journal payloads.
- Expired content is immediately excluded and physically removed by an explicit purge operation. Safe metadata has a separate bounded retention.
- Fresh store instances resume saved history/results. State/audit failures roll back together. CLI/HTTP and earlier iterations pass all reproducible checks.
